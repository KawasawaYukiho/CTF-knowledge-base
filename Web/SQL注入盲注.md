# SQL 注入盲注（ORDER BY / SQLite 函数绕过）

> **所属分类**：Web ｜ **难度参考**：中等
> **适用题型**：给了源码、存在 `ORDER BY` 等不可用 UNION 的拼接点、又被黑名单封死比较/逻辑运算符、页面无报错回显，只能靠"排序是否变化"判断真假的注入题。

## 一、知识点原理讲解

### 1.1 ORDER BY 注入为什么特殊

普通 `WHERE`/`LIKE` 注入可以直接 `AND substr(...)='x'`，但注入点落在 `ORDER BY` 后面时：

```sql
SELECT ... FROM files WHERE is_secret = 0 ORDER BY <这里被拼接>
```

`ORDER BY` 后面接的是**列名或表达式**，不能跟 `UNION SELECT`，也不能直接用 `=` 去比较某行内容。但它允许放**子查询和函数调用**，因此照样可以塞表达式，让数据库替我们算东西。

由于没有报错回显、也没有直接数据回显，只能靠"页面表现是否变化"来判断表达式真假——这就是**布尔盲注**。

### 1.2 布尔信号从哪来

盲注的前提是找到一个"可观测差异"。常见可观测差异有四种，任一可用即可：

- 排序结果是否反转；
- 返回记录条数是否变化；
- 页面响应时间是否变长（时间盲注）；
- 报错字符串是否出现（报错注入）。

本题场景里页面只有**两条公开记录**：一条名称以靠后的字母（如 `Z`）开头，一条以靠前的字母（如 `A`）开头。正常按 `id` 排序时 `Z` 那条在前；当我们把排序键改成"某条件"导致两行排序键大小关系翻转时，`A` 那条排到前面——**排序反转**就是"真"信号，**排序不变**就是"假"信号。

由此把任意数据库条件映射到"排序是否反转"上：

```
排序正常（Z 在前） → 条件为假
排序反转（A 在前） → 条件为真
```

### 1.3 双重黑名单下为什么传统盲注失效

很多这类题会叠两层过滤：

- **字符黑名单**封掉 `' " : ; = < > ! & | - + * /` 等 → 不能写字符串字面量、不能写比较运算、不能算术、不能堆叠查询。
- **关键词黑名单**封掉 `in/is/like/and/or/not/where/union/case/if` 等 → 不能写逻辑运算符、条件语句、WHERE、UNION/JOIN。

后果：`AND substr(col,1,1)='x'` 这种标准盲注写法里引号、等号、`and` 全被封，直接失效。必须改用**数据库内置函数**把这些被封功能一个个替代掉。

### 1.4 可迁移的"函数替代武器库"（以 SQLite 为例）

黑名单没封掉的内置函数，恰好能顶上被封的功能：

| 被封功能 | 替代武器 | 作用 |
| --- | --- | --- |
| 引号 `'...'` | `char(n1,n2,...)` | 由 ASCII 码拼出字符串，如 `char(90)` = `'Z'` |
| 等号 `=` 比较 | `instr(s, sub)` | 子串出现位置，找不到返回 0，找到返回 ≥1 |
| 逻辑与 `and` | `min(a,b)` | 两个数同时 >0 时取出来才 >0，等价"都成立" |
| 逻辑或 `or` | `max(a,b)` | 任一 >0 即 >0，等价"有一个成立" |
| 逐字符取数 | `substr(s, start, len)` | 固定截取某一位 |
| 缩小字符集 | `hex(s)` | 先转十六进制，每位置只猜 16 个 hex 字符 |
| 绕过 WHERE 筛行 | `group_concat(col)` | 子查询里聚合整表所有行成一个串，绕过外层 `WHERE` |
| 取长度 | `length(s)` | 配合 substr 定位到结尾 |

### 1.5 信号 payload 的通用构造

核心思路：让两条公开记录的排序键差异，受控于我们猜的条件。以"`Z` 开头的那条"为参照：

- `instr(name, char(90))`（即 `instr(name,'Z')`）：`Z` 那条返回 1，`A` 那条返回 0。
- 再用 `min(...)` 把"我们的条件"并进去：

```sql
min(instr(name, char(90)), <我们的条件表达式>)
```

- 当条件为假（取 0）：两行排序键都归 0，排序不变 → 假。
- 当条件为真（取 >0）：`Z` 那条排序键为 1、`A` 那条为 0，排序反转 → 真。

`min()` 在这里顶替了被封的 `and`，把"参照行本身含有 Z"与"我们猜的条件"绑定成同一个布尔量。

### 1.6 逐字符提取的标准姿势

1. 先用子查询 `(SELECT group_concat(col) FROM tbl)` 把整表（含被外层 `WHERE` 隐藏的行）聚合成一个串，绕过外层过滤。
2. 对它套 `hex(...)` 变成纯 `0–9 A–F` 的串。
3. 用 `substr(hex串, 位置, 1)` 逐位取，每一位遍历 16 个 hex 字符，命中即记录。
4. 拼出完整 hex 后转回明文。

这样把"对 95 个可打印字符逐位爆破"压缩成"每位置只猜 16 个 hex"，速度和稳定性都高得多。

### 1.7 识别特征

- 题目提供"查看源码"，且源码里有 `ORDER BY $_GET[...]` 之类直接拼接 → ORDER BY 注入。
- 过滤规则把 `= < > ' " and or where` 一锅端 → 走纯函数替代路线。
- 页面只有 2–3 条可排序数据 → 用排序反转做布尔信号。
- 数据库是 SQLite → 优先想到 `sqlite_master`、`group_concat()`、`char()`。

## 二、通用解题思路 / 套路

```
拿源码 → 定位 ORDER BY 拼接点
→ 分析过滤层（字符黑名单 + 关键词黑名单），列出"被封功能"清单
→ 找一个可观测差异（排序反转），先手动测一两次确认信号方向
→ 搭通用 payload 框架：min(instr(参照列,char(参照首字母)), 条件)
→ 用子查询 + group_concat 绕过 WHERE，先枚举库表结构（如 sqlite_master）
→ hex() + substr() 逐字符提取目标列，解码
→ 得到被隐藏的机密行/字段即目标
```

通用步骤清单：

1. **先建信号再猜数据**：动手前先用 `substr(name,1,1)` 之类测一次，确认"什么样的页面算真、什么样算假"。
2. **黑名单绕过三板斧**：字符串用 `char()`、相等比较用 `instr()`、逻辑与/或用 `min()/max()`。
3. **想绕 WHERE 就子查询聚合**：`(SELECT group_concat(col) FROM tbl)` 一次拿全表。
4. **逐字符一律先 hex 再 substr**，把字符集压到 16 个。
5. **注意 URL 编码与限速**：逗号、括号等要 URL encode；逐字符请求要加小延时，避免被临时封 IP。

易错点：

- 把 `and`/`or` 直接写进 payload，被关键词黑名单当场拦截。
- 忘了对注入表达式做 URL 编码，逗号/括号导致请求格式错误。
- 猜解太快触发 WAF 临时封禁，脚本里加 `time.sleep`。
- 没先确认信号方向就盲猜，结果把真假读反。

## 四、实战例题

### 例题 1：给了 PHP 源码、`ORDER BY` 拼接、双重黑名单的 SQLite 盲注题

- 题型特征：页面提供"查看源码"，源码中 `$order = $_GET['order']` 直接拼进 `ORDER BY $order`；外层过滤同时封字符与关键词；页面只返回两条公开文档记录。
- 解题思路：
  1. 代码审计确认注入点在 `order` 参数，且无报错回显，只能盲注。
  2. 手动请求 `order=substr(name,1,1)`，观察到两条公开记录排序反转，确立"排序反转=真"的布尔信号。
  3. 探测列名：`order=id/name/upload_date` 成功，其余报错；得知目标不在独立列，而藏在被 `WHERE is_secret=0` 隐藏的某一行 `name` 里。
  4. 用 `min(instr(name,char(90)), 条件)` 作通用框架，子查询 `group_concat(name) FROM sqlite_master` 枚举表结构。
  5. 子查询 `hex(group_concat(name)) FROM files` 聚合全表，逐字符猜 hex，解码后除两条公开记录外多出一条机密记录，即目标。
- 关键工具/脚本：`script/SQL注入盲注/SQL.py`（自动逐字符猜 hex 并解码）。
- 结果：得到被隐藏的机密记录，即flag。
